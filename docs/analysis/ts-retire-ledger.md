# TypeScript retirement: coverage ledger

This ledger maps every test case that PR 2 (Bun-free Rust tests) or PR 3 (delete the TypeScript
servers) of the retirement stack deletes to what keeps its proof. It is the acceptance list for PR 1
(freeze and coverage ledger, additive). Case counts are accounting, not acceptance: one Rust test or
fixture suite may carry many rows, and every row names the behaviour it keeps.

Snapshot: `origin/main` 41d6f98 (after #21 and #22), branch `feat/ts-retire-freeze`.

PR 1 is split into four additive PRs, each reviewed on its own (lead decision, taskr 80757). Each
fills the rows of its suites; PR 2 starts after all four have merged:

- **1a**: this ledger, the Krónan OpenAPI byte-hash gate, and family-store: golden formats, the
  store-record persistence matrix, Rust-versus-Rust process tests in place of
  `rust/family-store/tests/interop.rs`, and the `session-store` and `mcp-runtime` rows;
- **1b**: kronan-mcp and dominos-mcp;
- **1c**: inna-mcp;
- **1d**: abler-mcp and infomentor-mcp.

## Enumeration

```sh
node tooling/ts-freeze/ledger.mjs list       # one tab-separated line per case: suite, file:line, name, variants
node tooling/ts-freeze/ledger.mjs check      # the self-check, then: every case has exactly one complete row here, and every target exists
node tooling/ts-freeze/ledger.mjs selfcheck  # the adversarial self-check alone
```

The enumerator is static, so a reviewer can rerun it on any checkout. It reads tokens, not lines
(comments, strings, templates and regular expressions are skipped whole), so a registration is
found wherever it sits: in a helper or loop, after an `if`, with space or a line break before its
`(`. It reads:

- every `test`/`it` registration in `packages/*/test/**/*.test.ts` (the five servers, `mcp-runtime`
  and `session-store`) and `rust/*/tests/ts/**/*.test.ts` (the drop-ins), with its modifiers
  (`skip`, `only`, `todo`, `skipIf(…)` and the like) and the `if (…)` and
  `(… ? test : () => undefined)` platform forms. A registration in a loop or helper is one source
  site; its variants column lists the loop values, each a run-time case;
- the `scenarios` array of each `rust/*/tests/ts/parity.ts`: the `name` of each element object, or
  of each object a spread element maps to (a mapped or interpolated name is a loop site). A `name`
  key nested deeper (a cookie, a call) is data. Domino's parity has no named scenarios, so its rows
  are its argument list, tool surface, invalid-input list and unsafe-folder check (each found
  exactly once), the scenarios of `money-parity.ts`, and one row each for `reads-parity.ts` and
  `auth-parity.ts`;
- every `#[test]` function of a `rust/*/tests/*.rs` file that reads `FAMILY_MCP_BUN`, ignored
  helpers included;
- every other file under those test trees, listed below as harness files that carry no assertion of
  their own.

A form it cannot read stops the run instead of yielding no case: an aliased, namespace or
`describe` import from `bun:test`, a computed (`test[…]`) or unknown (`test.each`) member, `test`
used other than as a call, a test name that is not one literal, a scenario `name` that is not
`name: value`, and any Rust test attribute other than `#[test]`. Cases are keyed by their full site
and name; two cases with one identity stop the run, and two same-name sites are two cases. `check`
first runs the self-check, which feeds each of these forms (and the plain, modifier, helper, inline
`if`, spaced, split, commented, conditional and looped forms) to the enumerator and fails unless
each is either found, so that a ledger without its row fails, or refused.

The token-aware enumerator found four Domino's `money-parity.ts` sites the earlier line-based one
had missed (mapped scenario names, 30 run-time scenarios); they are rows here since the 1a review
(finding 1). Every other case is unchanged.

`check` also reads every row's target (review of PR #24). Each Rust test it names
(`rust/<crate>/<dir>/<file>.rs::[<module>::]<fn>`, or `<file>.rs::<fn>` in the row's own crate's
`tests/`) must be a `#[test]` (or `#[tokio::test]`) function in that file, so a name `--exact`
would run no test fails. Each fixture it names (`<server>/<set>/<case>`, `{a,b}` alternatives
expanded) must be a frozen file its crate's tests read: a `parity` or `contract` case named in
`tests/replay.rs`, a `store` state named in a test file, `pty` outcomes frozen for macOS and Linux
beside a `prompt.rs` test of that name, and `<set>/*` a set with its PROVENANCE.md that
`tests/replay.rs` replays. An existing-test row needs at least one implemented test, a new-test row
a Rust test, a fixture row a fixture or test. The one exemption is a target written
`planned <target>`: a name in a crate whose PR has not landed (1c inna-mcp, 1d abler-mcp and
infomentor-mcp), which must not exist yet; `check` fails on a `planned` target that exists, so each
PR unmarks its own as it implements them. The self-check feeds the check rows that must pass and
rows that must fail (a missing or prefix-only name, a function without a test attribute, an
unread or absent fixture, a planned target that exists).

## Outcomes

- **fixture row**: a deterministic contract (CLI text and exit codes, errors, tool schemas and
  results, pure transforms, expected request shapes) frozen once from the TypeScript reference at
  41d6f98 against loopback fakes only, with provenance (commit, Bun version, generator command,
  case ids, normalization rules) beside the fixtures. `rust/<crate>/tests/replay.rs` replays every
  row through the Rust binary and asserts the number of rows it loaded. A replay executes the binary
  step by step against a fake that serves the recorded responses, and compares outputs, exit codes,
  the full request list (method, path, body, count and order), the stored record and the files left
  behind. Ids are `<server>/<suite>/<case>`.
- **existing Rust test**: a Rust test that already proves the same assertion. The target names the
  function, not just the file. A row counts only once someone has read both test bodies and
  confirmed the Rust test asserts the same behaviour; a similar name is not enough. The PR that
  fills a row adds `verified <date> (<PR>)` to its target (1a: the store and runtime rows; 1b to 1d:
  theirs). Where the Rust test proves less, the row becomes a new executing Rust test that does.
- **new executing Rust test**: behaviour that depends on time, state, concurrency, signals, a
  terminal, durable writes, locks, retries, or the number and order of network sends. It runs the
  Rust binary or crate against loopback fakes and observes the effect itself; fixtures may supply its
  data but never replace the observation. Targets are planned names (`rust/<crate>/tests/<file>.rs::<fn>`);
  PR 1 replaces each planned name with the implemented one.
- **obsolete**: the case only exercises deleted TypeScript machinery, or it is a TypeScript run of a
  case whose run against the binary has its own row. The target gives the reason.

Parity rows in the safety categories are fixture rows on three conditions (lead decision, taskr
80757), which the replay engine and these rows keep:

1. every money and auth replay asserts the full request list (method, path, body, count, order),
   the journal or record state and the files left behind; output text alone is never enough;
2. for each crate, a mutation proves that one money replay fails on an extra send and one fails on
   a changed journal state (recorded in the PR report);
3. timing- and restart-dependent behaviour (a lost response, a restart or kill mid-send, renewal
   timers, lock takeover) stays in its dedicated executing row; a replay never stands in for it.

Categories: `money` (one-send consequential writes: orders, payments, absence requests),
`auth/renewal`, `pty/signal`, `lock/store` (store, migrate and logout precedence, locks, durable
files), `contract`, `other`.

Special rows:

- The PTY drivers (`rust/{kronan,inna,dominos}-mcp/tests/prompt.rs`) are kept. Only their
  TypeScript run is replaced, by frozen per-platform outcomes (terminal mode restored, exit code or
  signal, the saved value, the Linux hang-up outcome set).
- `surface.ts` regenerates `rust/*/src/surface.json`, which the servers embed. Comparing tools/list
  with that same file would be tautological, so the replaced contract is checked apart from it
  (lead 81512): `tests/replay.rs` compares the binary's tools/list with the frozen TypeScript list
  (`<server>/parity/surface`), so a change to `surface.json` fails there, and the frozen fixtures
  call every listed tool with a valid and with an invalid input, each answer compared with the
  frozen TypeScript one. A deliberate surface change then changes a reviewed fixture.
- Krónan's `api-types.test.ts` compile-time check maps to the request and response shape fixtures,
  the OpenAPI byte-hash gate (PR 1 step 2) and the reviewed-shapes pin; the compile-time
  spec-to-schema type check is an admitted gap.
